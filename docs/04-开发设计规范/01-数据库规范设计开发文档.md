## 2. 命名规范

### 2.1 表命名规范

| 规则     | 说明                 | 示例                           |
| ------ | ------------------ | ---------------------------- |
| 小写蛇形命名 | 所有表名使用 snake\_case | `bookings`, `room_types`     |
| 复数形式   | 表名使用英文复数           | `users` 而非 `user`            |
| 关联表    | 使用两个实体名拼接          | `user_roles`, `user_hotels`  |
| 前缀禁止   | 不使用 tbl\_ 等前缀      | `bookings` 而非 `tbl_bookings` |

### 2.2 字段命名规范

| 规则     | 说明                 | 示例                                    |
| ------ | ------------------ | ------------------------------------- |
| 小写蛇形命名 | 所有字段使用 snake\_case | `hotel_id`, `check_in_date`           |
| 主键统一   | 使用 `id` 作为自增主键     | `id INT AUTO_INCREMENT PRIMARY KEY`   |
| 外键命名   | 关联表名\_id           | `hotel_id`, `user_id`, `room_id`      |
| 布尔字段   | 使用 is\_ 前缀         | `is_used`, `is_multiple_use`          |
| 时间字段   | 使用 \_at 后缀         | `created_at`, `updated_at`, `paid_at` |
| 状态字段   | 使用 \_status 后缀     | `room_status`, `device_status`        |
| 编号字段   | 使用 \_number 后缀     | `booking_number`, `room_number`       |
| 金额字段   | 使用 DECIMAL(10,2)   | `total_price`, `balance`              |

### 2.3 索引命名规范

| 索引类型 | 命名格式          | 示例                              |
| ---- | ------------- | ------------------------------- |
| 唯一索引 | `uk_字段名`      | `uk_phone`, `uk_booking_number` |
| 普通索引 | `idx_字段名`     | `idx_hotel_id`, `idx_status`    |
| 联合索引 | `idx_字段1_字段2` | `idx_order_type_order_id`       |

## 3. 角色定义规范

### 3.1 系统角色体系

系统采用四级角色体系，角色值存储在 `users.role` 字段中：

| 角色标识          | 角色名称  | 角色代码          | hotel\_id | 说明            |
| ------------- | ----- | ------------- | --------- | ------------- |
| system\_admin | 系统管理员 | SYSTEM\_ADMIN | 0         | 管理所有酒店，可跨酒店操作 |
| hotel\_admin  | 酒店管理员 | HOTEL\_ADMIN  | 具体酒店ID    | 管理所属酒店        |
| staff         | 前台员工  | STAFF         | 具体酒店ID    | 操作所属酒店业务      |
| customer      | 顾客    | CUSTOMER      | **0**     | 顾客不属于特定酒店     |

### 3.2 角色别名映射

系统支持多种角色别名，统一规范化处理：

| 规范值           | 允许的别名                                                          |
| ------------- | -------------------------------------------------------------- |
| system\_admin | system, sys\_admin, systemadmin, super\_admin, platform\_admin |
| hotel\_admin  | admin, manager, hotel\_manager, hoteladmin                     |
| staff         | receptionist, reception, front\_desk, frontdesk                |
| customer      | user, guest                                                    |

### 3.3 hotel\_id 策略（核心规范）

**hotel\_id 是系统中最重要的多租户隔离字段，必须严格遵守以下规则：**

| 角色            | hotel\_id 值 | 说明                 |
| ------------- | ----------- | ------------------ |
| system\_admin | 0           | 系统管理员不属于任何酒店，可查看所有 |
| hotel\_admin  | 对应酒店ID      | 绑定到管理的酒店           |
| staff         | 对应酒店ID      | 绑定到工作的酒店           |
| customer      | **0**       | 顾客不属于特定酒店，通过订单关联酒店 |

**关键规则：**

1. 顾客的 `hotel_id` 必须为 0，顾客通过 `bookings.hotel_id` 关联到具体酒店
2. 创建支付记录时，`hotel_id` 必须从关联的订单（bookings/delivery\_orders/maintenance\_tickets）中获取，不能从 `users.hotel_id` 获取
3. 更新订单状态时，不能使用 `hotel_id` 作为 WHERE 条件，应使用 `id` 主键
4. 前台/酒店管理员查询数据时，必须按 `hotel_id` 过滤

## 5. 开发约束

### 5.1 必须遵守的规则

1. **hotel\_id 来源规则**：创建支付/操作时，hotel\_id 必须从关联的业务订单中获取，禁止从 `users.hotel_id` 取值
2. **状态更新规则**：更新订单状态时，WHERE 条件使用主键 `id`，禁止使用 `hotel_id` 作为更新条件
3. **乐观锁**：bookings 表使用 `lock_version` 实现乐观锁，更新时必须检查版本号
4. **软删除**：核心业务数据不物理删除，使用状态标记（如 cancelled）
5. **时间字段**：所有表必须包含 `created_at` 和 `updated_at`
6. **金额精度**：所有金额字段使用 `DECIMAL(10,2)`，禁止使用 FLOAT/DOUBLE
7. **JSON字段**：facilities/images/photos 等使用 JSON 类型存储

### 5.2 禁止的操作

1. 禁止直接修改数据库中的状态值，必须通过 API 接口操作
2. 禁止在 WHERE 条件中使用 `hotel_id` 来更新跨表数据
3. 禁止将顾客的 `hotel_id` 设置为非零值
4. 禁止物理删除有业务关联的数据记录
