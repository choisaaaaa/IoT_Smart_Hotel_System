### 1.3 角色系统双重设计

#### 🔴 `users.role` (varchar) vs `user_roles` + `roles` 表

| 方式 | 存储 | 机制 |
|------|------|------|
| 方式1 | `users.role` 字段 | 直接存角色名字符串如 "system", "staff", "user" |
| 方式2 | `user_roles` + `roles` 表 | 标准RBAC，支持多角色 |

**后端鉴权实际使用的是 `users.role`：**

| 文件 | 代码 | 用法 |
|------|------|------|
| `backend/src/middleware/auth.ts:46` | `req.user = { ...decoded, role: normalizeRole(decoded.role) }` | JWT中的role直接使用 |
| `backend/src/controllers/booking.controller.ts:248` | `req.user?.role === 'user'` | 直接比较 users.role |
| `backend/src/controllers/booking.controller.ts:421` | `req.user?.role === 'reception' \|\| ...` | 直接比较 users.role |
| `backend/src/controllers/member.controller.ts:121` | `req.user?.role === 'user'` | 直接比较 users.role |
| `backend/src/controllers/payment.controller.ts:12,34` | `req.user?.role === 'user'` | 直接比较 users.role |
| `backend/src/controllers/room.controller.ts:13,50,78` | `isSystemRole(req.user?.role)` | 基于 users.role 判断 |
| `backend/src/utils/role.ts` | `normalizeRole()` | 角色名归一化映射 |

**`user_roles` 表仅在登录和审核时写入，但鉴权时不读取：**

| 文件 | 代码 | 用法 |
|------|------|------|
| `backend/src/routes/v1/auth.ts:195` | `FROM user_roles ur` | 登录时读取，但结果只用于确定 `users.role` 的值 |
| `backend/src/routes/v1/auth.ts:217` | `normalizeRole(userRoles.length > 0 ? userRoles[0].role_name : user.role)` | 优先用 user_roles，fallback 到 users.role |
| `backend/src/routes/v1/auth.ts:324` | `INSERT INTO user_roles` | 注册时写入 |
| `backend/src/routes/v1/auth.ts:610,614` | `DELETE/INSERT user_roles` | 审核通过时写入 |
| `backend/src/routes/v1/auth.ts:637,641` | `DELETE/INSERT user_roles` | 审核绑定时写入 |

**角色名混乱问题**：`normalizeRole()` 需要处理大量别名

```typescript
const ROLE_ALIASES = {
  sys_admin: 'system',
  systemadmin: 'system',
  system_admin: 'system',
  super_admin: 'system',
  platform_admin: 'system',
  receptionist: 'staff',
  front_desk: 'staff',
  frontdesk: 'staff'
};
```

**结论**：`user_roles` 表形同虚设，实际鉴权完全依赖 `users.role`。两套系统不同步，审核通过时同时修改两处，但登录时只读 `user_roles` 来辅助确定 `users.role`。

## 二、数据库层问题

### 🔴 严重问题

#### 2.1 缺少外键约束 — 数据一致性无保障

现有外键仅15个，缺失的关键外键：

```sql
-- 缺失的外键约束
bookings.hotel_id       → hotels.id       ❌
coupons.hotel_id        → hotels.id       ❌
payments.hotel_id       → hotels.id       ❌
role_applications.hotel_id → hotels.id    ❌
room_prices.hotel_id    → hotels.id       ❌
user_hotels.hotel_id    → hotels.id       ❌
delivery_orders.booking_id → bookings.id  ❌
maintenance_tickets.booking_id → bookings.id ❌
control_commands.device_id → devices.device_id ❌
```

**影响**：可以删除一个酒店但留下它的房间、预订、支付等孤儿数据。

#### 2.2 `sensor_data` 表无分区/归档策略

- 传感器数据会爆发式增长
- 没有按时间分区，查询会越来越慢
- 没有 TTL（数据过期自动清理）机制

#### 2.3 时间字段命名不统一

- 有的表用 `created_at` / `updated_at`
- 有的用 `started_delivering_at` / `completed_at` / `assigned_at`
- `payments` 表有 `expired_at` 但数据库列定义中查不到

## 三、后端层问题

### 🔴 严重问题

#### 3.1 通话逻辑三处重复实现

```
call.controller.ts  → initiateCall() 里有完整的通话逻辑(~80行)
call.service.ts     → initiateCall() 里有几乎相同的逻辑(~60行)
websocket.service.ts → initiate_call 事件里又有类似逻辑(~50行)
```

**三处代码生成callId的方式都不同**：
- controller: `CALL${date}${uuidv4().slice(0,8)}`
- service: `CALL${date}${uuidv4().slice(0,8)}`
- websocket: `CALL${date}${Math.random().toString(36).substring(2,10)}` ← 不安全

#### 3.2 `SELECT *` 泛滥 — 71处

```sql
SELECT * FROM users WHERE phone = ?       -- 可能泄露密码hash
SELECT * FROM role_applications WHERE ...  -- 返回不必要字段
SELECT * FROM members WHERE phone = ?      -- 返回不必要字段
... 共71处
```

#### 3.3 `hotel.controller.ts` vs `hotels.controller.ts` 命名混乱

| 文件 | 路由 | 用途 |
|------|------|------|
| `hotel.controller.ts` | `/hotel` | 单酒店管理（管理员用） |
| `hotels.controller.ts` | `/hotels` | 酒店搜索/列表（客户端用） |

两者功能边界模糊，都操作 `hotels` 表。

#### 3.4 业务逻辑直接写在路由文件中

`auth.ts` 有 630+ 行，包含：
- 角色申请审核逻辑
- 创建酒店逻辑
- 修改用户角色逻辑
- 数据库事务操作

这些都应该在 service 层。

#### 3.5 错误处理不一致

```typescript
// 方式1: errorResponse
res.status(400).json(errorResponse('请求参数错误'));

// 方式2: 直接构造
res.status(401).json({ code: 401, message: '未提供认证令牌', timestamp: Date.now() });

// 方式3: sendError
return sendError(res, errorResponse('用户不存在', 404));
```

#### 3.6 事务使用不一致

- `booking.controller.ts` 正确使用了 `pool.getConnection()` + 事务
- `auth.ts` 中的审核逻辑直接多条 `connection.execute`，没有事务包裹
- 如果创建酒店成功但更新用户角色失败，数据就不一致了

### 🟡 中等问题

#### 3.7 缺少输入验证层

- 没有使用 `joi` / `zod` / `express-validator` 等验证库
- 参数校验全靠手动 `if (!xxx)` 判断

#### 3.8 数据库连接未使用连接池最佳实践

- 直接 `import pool` 全局共享
- 没有连接池大小配置
- 没有连接超时/空闲回收策略

## 四、硬件接口层问题

### 🔴 严重问题

#### 4.1 MQTT与WebSocket职责边界模糊

```
MQTT:  硬件 → 后端 (设备状态/传感器数据/指令结果)
WebSocket: 前端 ↔ 后端 (实时通知/通话信令/设备控制)

但通话信令同时出现在两个通道：
- MQTT: hotel/call/signaling/+ 和 hotel/call/audio/+
- WebSocket: initiate_call / webrtc_offer / webrtc_answer / webrtc_ice_candidate
```

硬件发起通话走MQTT，前端发起通话走WebSocket，但两者之间没有统一的信令协调层。

#### 4.2 WebSocket `clients` Map 只存内存

```typescript
private clients: Map<string, ClientInfo> = new Map();
```

- 服务器重启后所有客户端需要重新注册
- 没有持久化在线状态
- 没有与数据库 `devices` 表同步

#### 4.3 WebRTC 信令缺少 TURN 服务器配置

```dart
final Map<String, dynamic> _iceServers = {
  'iceServers': [
    {'urls': 'stun:stun.l.google.com:19302'},  // 只有STUN，没有TURN
  ]
};
```

NAT穿透在对称型NAT下会失败，酒店网络环境下没有TURN意味着大量通话无法建立。

#### 4.4 音频流转发效率极低

```typescript
// websocket.service.ts 中 handleCallAudio
async handleCallAudio(topic: string, message: Buffer) {
  // 每收到一个音频包就查一次数据库找接收者
  const [rows] = await pool.query<RowDataPacket[]>(
    'SELECT caller_type, caller_id, callee_type, callee_id FROM calls WHERE call_id = ?',
    [callId]
  );
```

音频是实时流，每秒几十个包，每个包都查数据库是不可接受的。

### 🟡 中等问题

#### 4.5 MQTT重连策略不够健壮

- 最大重连10次后放弃，不自动恢复
- 没有指数退避上限后的定期心跳检测

#### 4.6 设备签名验证与业务逻辑耦合

- `handleMessage()` 方法同时负责签名验证和业务分发
- 应拆分为中间件模式：验证 → 路由 → 处理

## 五、Web端问题

### 🔴 严重问题

#### 5.1 WebSocket单例模式 — 全局只有一个连接

```typescript
let socket: Socket | null = null

export function initWebSocket(roomId?: string): Socket {
  if (socket?.connected) return socket  // 复用已有连接
```

- 不同页面需要不同的WebSocket行为，但共享一个连接
- 事件监听器在 `initWebSocket` 中硬编码，无法按页面动态注册/注销
- 如果用户切换页面，旧页面的事件处理器仍然在执行

#### 5.2 Token存储混乱 — 两个地方存，读取时做兼容

```typescript
function getAuthToken(): string {
  const rawToken = localStorage.getItem('auth_token')     // 存储位置1
  const rawUserInfo = localStorage.getItem('user_info')   // 存储位置2
  // 从 user_info 中提取 token 作为 fallback
}
```

#### 5.3 角色判断逻辑分散

- `router/index.ts` 中有 `normalizeRole()` 做路由守卫
- `api/auth.ts` 中也有角色判断
- 各Layout组件中还有角色判断
- 三处逻辑需要保持同步

### 🟡 中等问题

#### 5.4 Pinia Store 职责不清

`app.ts` store 既管UI状态(侧边栏折叠)，又管认证状态(userInfo)，又管通话状态(incomingCall/currentCall)。应拆分为 `uiStore`、`authStore`、`callStore`。

#### 5.5 视图组件复用度低

- `PriceCalendar.vue` 和 `CouponManage.vue` 在 admin 和 reception 路由中重复引用（同一组件）
- 但 `EnvironmentMonitor.vue` 却有 admin 和 reception 两个不同版本

## 六、App端问题

### 🔴 严重问题

#### 6.1 巨型文件 — `dashboard_page.dart` 882行，包含6个页面类

```
ReceptionDashboardPage (外壳)
├── _ReceptionHomeContent (总览)
├── CheckInOutPage (入住退房) ← 应该独立文件
├── BookingsPage (预订) ← 应该独立文件
├── PriceSettingsPage (房价设置) ← 应该独立文件
└── 语音通话/设备管理等内容
```

违反单一职责原则，热重载时整个文件重新编译，代码冲突概率高。

#### 6.2 VoiceCallService 单例但 init 有防重入问题

```dart
void init(String userId, {String clientType = 'front_desk'}) {
  if (_isInitialized) return;  // 第二次调用直接返回，无法重连
```

如果用户下线再上线，`_isInitialized` 为 true 导致 `init` 直接返回，WebSocket不会重新连接。

#### 6.3 API路径拼接不一致

```dart
// call_api_service.dart
'${ApiConstants.calls}/outbound'   // 可能产生双斜杠

// dashboard_page.dart
'${ApiConstants.calls}$callId/hangup'  // 正确
```

#### 6.4 缺少统一的错误处理和加载状态管理

- 每个页面都自己写 `try/catch` + `setState(() => _isLoading = false)`
- 没有统一的 `ApiResult` 到 UI 的映射
- 网络错误提示不统一

### 🟡 中等问题

#### 6.5 Models 层不完整

```
models/ 目录只有: booking, device, hotel, room, user
缺失: call, delivery, maintenance, coupon, member, payment
```

大量页面直接用 `Map<String, dynamic>` 操作数据，没有类型安全。

#### 6.6 Service 层风格不统一

- 有的 Service 返回 `ApiResult<T>`（如 CallApiService）
- 有的 Service 返回原始 `Response`（如 DioClient 直接调用）
- Dashboard 页面直接用 `DioClient().post()` 跳过 Service 层

## 八、优化建议路线图

### 第一阶段：修复关键问题（建议优先处理）

1. **数据库字段清理**
   - 废弃 `star_rating`，统一使用 `hotel_star`（改动最小，因为大部分代码已用 `hotel_star`）
   - 废弃 `location`，统一使用 `hotel_address` + `city`
   - 删除从未使用的 `hotels.hotel_id`、`hotels.hotel_code`、`hotels.promotion`
   - 删除从未使用的 `rooms.room_id`、`rooms.image_url`
   - 逐步废弃 `rooms.room_type`(varchar)，统一使用 `rooms.room_type_id`(FK)

2. **通话逻辑统一**
   - 将三处通话逻辑合并到 `CallService`
   - controller 和 websocket 都调用 service
   - 统一 callId 生成方式

3. **VoiceCallService 重连修复**
   - 增加 `reset()` 方法，清除 `_isInitialized` 标志
   - 支持断线重连

4. **App 巨型文件拆分**
   - 将 `dashboard_page.dart` 中的 CheckInOutPage、BookingsPage 等拆为独立文件

### 第二阶段：架构优化

5. **补全外键约束**：逐步添加缺失的外键
6. **统一错误处理**：后端统一用 `errorResponse`，App端统一用 `ApiResult`
7. **添加输入验证层**：后端引入 `zod` 做 request validation
8. **补全 App Models 层**：为所有数据结构创建类型安全的 Model 类
9. **角色系统统一**：选择一种方式（建议保留 `users.role`，废弃 `user_roles` 表的复杂逻辑，或反过来完全迁移到 RBAC）

### 第三阶段：性能与安全

10. **添加 TURN 服务器**：部署 coturn 解决 NAT 穿透
11. **sensor_data 分区**：按月分区 + 定期归档
12. **WebSocket 在线状态持久化**：Redis 存储，支持服务重启恢复
13. **消除 SELECT ***：所有查询明确指定字段列表
14. **音频流转发优化**：内存缓存通话映射关系，避免每包查数据库
