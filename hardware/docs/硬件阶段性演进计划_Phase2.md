# 智慧酒店硬件组 - Phase 2 演进任务与实装计划 (To-Do List)

> **文档定位**：
> 本文档记录了在完成基础三层硬件解耦架构（Phase 1）之后，**仅限于硬件层面（无需等待其他组提供接口）可独立完成的系统级加分项与可靠性演进计划**。
> 以下任务旨在将《硬件架构与设计基线_v1.0.md》中规划的生产级安全与运维要求，全面转化为可执行的底层固件代码。

---

## 1. 🛡️ 安全架构演进 (Security)

### 1.1 业务代码配置收敛 (消除“三端行为漂移”)
- **现状缺陷**：当前客房端、前台端的 `main.c` 业务代码中存在硬编码的门禁扇区密钥（`{0xFF, 0xFF, ...}`）及客户端鉴权 ID（`front_desk_01`）。
- **实装目标**：
  - 所有敏感密钥、密码及终端 ID 严禁出现在应用层代码中。
  - 全面重构 `service_network_read_nvs_string()` 函数。
  - **验收标准**：设备初始上电时，通过 Web 强制配网（Captive Portal）输入配置数据并存入 NVS 物理加密分区。后续 `main.c` 仅通过 NVS 接口进行提取与鉴权。

### 1.2 通信链路双向加密 (TLS)
- **现状缺陷**：底层 MQTT 服务当前采用明文 `mqtt://` 协议，存在极大的局域网抓包风险。
- **实装目标**：
  - 升级 `common_components/service_mqtt` 模块。
  - 接入 MbedTLS 栈，将连接 URI 强制切换为 `mqtts://` (端口 8883)。
  - **验收标准**：客户端内置 CA 根证书，实现与后台服务器的证书级双向身份认证。

## 2. ⚡ 高可靠性与容灾 (Reliability)

### 2.1 核心链路防丢策略 (QoS 升级)
- **现状缺陷**：当前示例代码默认使用 QoS 0，在复杂 WiFi 漫游及高遮挡的酒店网络环境下，极易发生门禁开启或火警广播指令丢失。
- **实装目标**：
  - 将所有与“强电控制（开锁/断电）”及“安防告警（SOS/烟雾）”相关的 `service_mqtt_publish` 与 `subscribe` 函数调用的 QoS 级别全面升级为 **1 (至少送达一次)** 或 **2 (精确送达一次)**。
  - **验收标准**：人为制造断网环境测试，核心消息在网络恢复后能够被准确接收且不发生重放。

### 2.2 离线边缘自治缓存 (Local Cache)
- **实装目标**：
  - 针对大面积断网等极端异常情况，客房端需在本地 Flash 缓存最新的下发门禁白名单及房间配置。
  - **验收标准**：断网期间断开与 MQTT 的连接，离线刷卡依然能够比对缓存验证开门，并在网络恢复连接后批量补发离线流水日志。

## 3. 📊 生产级运维监控 (Ops & Health Monitor)

### 3.1 设备原生心跳自检模块
- **现状缺陷**：当前缺乏统一的固件级故障预警手段，无法提前预判因堆内存泄漏或 WiFi 信号衰减导致的设备死机。
- **实装目标**：
  - 在 `common_components` 内新增独立的「健康心跳 (Health Monitor)」后台守护任务。
  - 周期性（如每 10 分钟）调用 ESP-IDF 原生 API 获取底层状态。
  - **上报字段**：
    - `uptime_sec`: 设备连续在线时长
    - `free_heap_bytes`: 剩余可用堆内存
    - `wifi_rssi`: 当前 Wi-Fi 信号强度
    - `reconnect_counts`: 历史网络重连次数
  - **验收标准**：该模块作为黑盒组件，在任意终端 `main.c` 调用 `service_health_monitor_start()` 即可自行在后台向后台遥测节点发送标准的 JSON 健康报告。

---

## 4. 🧱 组件池边界守卫 (Architecture Governance)

- **组长代码审查规范 (Code Review)**：
  - 坚决杜绝“高速公路被绕路掏空”现象。
  - **红线规则**：任何组员在引入新的硬件外设（如毫米波雷达、烟雾传感器等）时，**绝对禁止在其负责终端的 `main.c` 中直接操作底层 GPIO 或 I2C 寄存器**。
  - 所有新外设的驱动与状态轮询，必须先合入 `common_components/hal_sensors` 等底层组件池，提供标准的 `.h` 对外接口后，方可被业务层调用。
