## 1. 设计思路

### 一、系统总体设计思路

本系统面向智慧酒店“多角色运营 + 多区域设备 + 实时服务联动”的实际场景，采用“云端平台 + 本地三端硬件”的总体架构。设计遵循以下核心原则：

1. **分层解耦**：将业务规则、设备控制、界面展示与数据存储职责分离，降低耦合风险。
2. **终端自治与平台统筹并存**：硬件端保持最小本地可执行能力，平台负责全局编排、策略与审计。
3. **统一协议与统一标识**：通过 MQTT 主题规范、设备 ID 命名与状态模型统一，实现跨端协同。
4. **可扩展与可演进**：保留从原型验证到正式打板、从单门店到多门店扩展的升级路径。
5. **安全与可靠性前置**：在架构层预留 TLS、设备认证、离线自治与健康监测能力。

当前总体结构如下：

- **本地硬件终端层**：由客房端、前台端、楼控端三类 ESP32-S3 节点组成，按区域部署于酒店现场，负责感知、执行与状态反馈。
- **平台服务层**：负责业务数据、设备接入、指令调度、状态汇聚、日志审计与 AI 能力编排。
- **前端应用层**：面向不同业务角色提供可视化与操作入口，承接管理、服务与客户交互。
- **移动应用层**：提供移动办公与住客自助服务能力，保证业务触达场景完整。

该架构确保了“硬件控制链路可闭环、平台业务可治理、前端体验可扩展”三项核心目标。

### 二、业务角色与软件系统设计

系统按业务角色进行功能分区，避免单入口承载过多异构需求。角色与系统对应关系如下：

1. **集团/系统管理角色**：负责多门店配置、资源统筹、全局策略与运维监管。
2. **门店管理/前台执行角色**：负责入住退房、房态管理、发卡与应急处置。
3. **住客用户角色**：负责预订、服务请求、客房内设备控制与语音交互。

软件系统设计要点如下：

- **后端系统（Node.js + Express + TypeScript）**
  - 架构形态：控制层、服务层、数据访问层分层组织。
  - 通信能力：`mqtt`、`socket.io`，并支持 REST API。
  - 数据能力：MySQL 持久化 + Redis 缓存与加速。
  - 安全能力：JWT、限流、参数校验、审计日志。
  - 作用定位：系统业务核心与设备管理核心。

- **Web 前端（Vue3 + Vite + TypeScript）**
  - UI 框架：Ant Design Vue。
  - 状态管理：Pinia。
  - 图表展示：ECharts。
  - 实时联动：Socket.io Client。
  - 作用定位：管理视图、前台操作视图、监控与统计视图。

- **移动端（Flutter）**
  - 网络协议：HTTP、WebSocket、MQTT（按业务场景接入）。
  - 音视频能力：预留 WebRTC 能力用于实时语音业务。
  - 作用定位：移动化管理入口与住客服务入口。

通过角色化系统设计，平台可在“运营效率、服务体验、权限安全”三方面形成稳定闭环。

### 三、多终端协同组网与设备统一管理

本系统采用“前台端 - 楼控端 - 客房端”的分布式组网模式。三端通过 WiFi 接入 MQTT Broker，与平台形成发布/订阅协同：

- **前台端（Front Desk）**
  - 核心职责：发卡、房态展示、人工介入与应急广播触发。
  - 关键外设：RC522、WS2812、按键、蜂鸣器。

- **楼控端（Floor Controller）**
  - 核心职责：公共区域感知、走廊照明与报警联动。
  - 关键外设：MQ-2、光敏、NTC、继电器、报警按键。

- **客房端（Room Terminal）**
  - 核心职责：门禁鉴权、客房设备控制、语音与前台交互。
  - 关键外设：RC522、4 路继电器、红外收发、I2S 麦克风/功放、按键/EC11、雷达。

设备统一管理设计要点：

1. **设备唯一标识与类型化路由**：按设备类型与设备 ID 进行主题分发和命令路由。
2. **统一状态上报模型**：上线状态、心跳、遥测、命令结果采用统一字段与主题口径。
3. **平台集中治理**：设备接入、状态监控、异常追踪在平台统一完成。
4. **防冒用与可追溯预留**：通过设备鉴权、审计日志、命令结果回执支撑追踪能力。
5. **扩展路径明确**：可按楼层、区域、门店横向扩容节点，不改变核心架构。

### 四、AI语音交互与智能化服务

系统将 AI 能力作为业务链路的一部分，而非孤立展示模块。当前设计采用“人机协同 + 人工兜底”的策略：

1. **语音入口设计**
   - 客房端以 PTT（按键触发）为主，不采用默认常开监听。
   - 目的：降低算力负担，控制隐私合规风险。

2. **语音处理链路**
   - 上行：终端采集语音数据，经平台进行语音识别与意图解析。
   - 推理：大模型完成语义理解与指令结构化。
   - 下行：生成设备控制指令与语音反馈。

3. **服务编排策略**
   - AI 优先处理高频标准请求（如空调、灯光、服务呼叫）。
   - 非标准请求可转人工前台介入，保证服务连续性。

4. **体验目标**
   - 从“固定按钮控制”升级为“自然语言控制”。
   - 在不增加终端复杂度的前提下，提升住客交互效率与满意度。

### 五、物联网通信与硬件实现

通信与硬件实现采用“轻量协议 + 本地执行 + 平台协同”的设计：

1. **通信协议选型**
   - 设备通信主通道：MQTT（发布/订阅）。
   - 管理界面实时推送：Socket.io。
   - 业务接口：REST API。

2. **硬件控制策略**
   - 主控统一：ESP32-S3 N16R8。
   - 代码组织：`driver -> hal -> service -> app(main)` 分层。
   - 引脚策略：冻结 Pinmap 统一配置，避免跨端冲突与漂移。

3. **稳定性策略**
   - 支持网络波动场景下的本地基本联动（如关键执行链路不依赖前端中转）。
   - 保留健康上报、消息重试、异常回执与日志追踪机制。

4. **阶段性口径**
   - 当前阶段：原型验证与联调可用。
   - 后续阶段：量产前需补齐 TLS 全链路、长稳报告、全外设在环验证与生产级认证机制。

## 2. 设计重点与难点

### 一、物联网设备通信与系统稳定性保障

**重点**：三端设备长期在线、指令到达可确认、状态反馈可追踪。  
**难点**：终端数量增长后，连接稳定性、订阅恢复、消息时序与弱网容错复杂度显著上升。

**应对策略**：
1. 统一设备生命周期管理（上线、离线、重连、异常）。
2. 关键链路采用命令回执机制，形成“下发-执行-反馈”闭环。
3. 网络波动时保持本地最小可执行逻辑，避免核心控制完全失效。
4. 通过健康上报与日志审计提升问题定位效率。

---

### 二、实时数据同步与高并发处理机制

**重点**：房态、设备状态、告警事件需实时同步到平台与前端。  
**难点**：高并发下连接管理、广播效率、数据库压力与消息风暴风险并存。

**应对策略**：
1. Web 层采用 Socket.io 主动推送，减少轮询成本。
2. Redis 承担热点数据与高频状态缓存，降低 MySQL 压力。
3. 采用事件分级与主题分层，控制无效广播范围。
4. 对关键链路设置限流、重试与超时保护，避免系统雪崩。

---

### 三、多角色权限管理设计

**重点**：不同角色访问边界必须清晰，接口权限与数据权限必须同步约束。  
**难点**：角色多、业务多、设备多导致权限粒度与维护成本提高。

**应对策略**：
1. 使用 JWT 认证与 RBAC（基于角色访问控制）模型。
2. 在接口层实施统一鉴权、参数校验与操作审计。
3. 对高风险操作（开锁、发卡、应急广播）增加二次校验与日志留痕。
4. 保持“最小权限”原则，避免角色越权访问。

---

### 四、复杂业务流程与数据一致性保障

**重点**：房态、订单、门禁、服务请求等多业务链路必须一致。  
**难点**：跨服务、跨终端、跨时序场景中容易出现状态不同步与幂等问题。

**应对策略**：
1. 明确领域对象状态机与状态迁移规则。
2. 关键事务采用原子更新与回滚策略，避免半成功状态。
3. 为设备命令引入请求 ID / 回执 ID，提升幂等与可追踪能力。
4. 通过对账任务与异常补偿机制兜底边缘场景。

---

### 五、系统扩展性与工程化部署能力

**重点**：系统要支持更多门店、更多设备、更多并发而不推翻架构。  
**难点**：原型阶段容易出现“功能可跑但不可运维、不可扩容”的隐患。

**应对策略**：
1. 模块化组织后端、前端、硬件三端代码，降低跨模块改动影响。
2. 采用标准化 API 与协议文档，保障多人协作一致性。
3. 支持容器化部署与环境参数化配置，提升交付与迁移效率。
4. 硬件侧坚持“前台-楼控-客房”分布式拓扑，可按区域横向扩容节点。
5. 保留从“原型接线版”到“集成打板版”的双文档通道，支撑阶段平滑切换。

## 3. 当前阶段结论与后续落地建议

### 3.1 当前阶段结论

1. 系统总体架构已形成闭环：硬件三端、平台服务、Web 与移动端可协同。
2. 硬件侧已完成冻结引脚与分板接线口径统一，具备持续联调能力。
3. 软件侧已具备角色化入口、设备通信链路与核心业务承载能力。
4. 当前状态适合“功能深化 + 稳定性强化”，不建议直接宣称量产就绪。

### 3.2 后续建议（面向 Phase2/Phase3）

1. 完成 TLS 与设备身份认证的全链路闭环验证。
2. 补齐长稳测试、弱网测试、异常恢复与容量压测报告。
3. 对关键场景（门禁、告警、广播）补充端到端验收用例矩阵。
4. 固化“原型验证版 / 集成打板版”文档同步机制，避免实现与文档漂移。
5. 推进多门店多区域管理视图与设备运维可视化能力。
