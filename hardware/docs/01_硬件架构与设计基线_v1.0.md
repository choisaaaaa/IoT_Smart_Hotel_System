# 智慧酒店物联网控制系统 - 硬件架构与设计基线 v1.0

## 0. 当前落地状态（2026-04-09）

- 三端独立构建通过：`room_terminal`、`front_desk_terminal`、`floor_controller`。
- MQTT 基础联调通过：上线、心跳/遥测、命令回执链路已可用。
- 配置策略已收敛：设备 ID 与 Broker URI 改为 NVS 优先、默认值兜底。
- 当前阶段定义：可联调稳定态（可支撑联合调试）；尚未进入量产稳定态（缺长稳与外设在环验证）。

## 1. 核心架构说明

根据项目最新决策，本系统的硬件架构采用**“全终端 WiFi/MQTT 直连后端”**模式。

- **通信链路**：所有硬件设备（前台端、楼控端、客房端）均作为独立的物联网边缘节点（IoT Edge Nodes）。
- **网络连接**：各设备通过内置 WiFi 直接接入局域网/互联网。
- **数据交互**：各设备运行完整的 MQTT 客户端，直接与后端的 MQTT Broker 建立 TCP 长连接进行指令订阅（Subscribe）与状态发布（Publish）。
- **解耦原则**：硬件设备产生的数据和事件，直接发送给后端服务器处理，**不通过前端网页（Vue）中转**，以降低客流高峰期前端的高并发压力。

## 2. 统一主控选型与公共组件库 (Common Components)

### 2.1 硬件选型基线
- **全系标配主控（冻结）**：`ESP32-S3 N16R8`
- **冻结说明**：本文档其余历史段落中若出现 `ESP32-WROOM-32`，以本条为准；旧表将在后续版本统一替换。
- **选择理由**：算力与外设能力更充足，适合本项目当前音频与多外设并行场景。

### 2.2 跨终端公共组件库 (Common Components)
为大幅提升协同开发效率，避免各端开发人员重复造轮子及底层 GPIO 冲突，本项目已正式建立并完善了**统一硬件组件池（`hardware/common_components`）**。
- **定位**：对所有底层驱动（I2C/SPI）、硬件抽象层（强电控制/传感器采集）及核心服务（配网/MQTT通信）进行了“黑盒封装”。
- **使用规范**：前台端、楼控端与客房端的应用层代码（`main.c`）**严禁直接操作底层寄存器或原始引脚 API**。必须统一引用 `common_components` 目录下的头文件（如 `hal_actuators.h`、`service_mqtt.h`），以业务语义调用高级 API。
- **详细接入教程**：请各开发人员参阅 [《核心组件池 (Common Components) 使用教程》](../common_components/USAGE_TUTORIAL.md) 获取 CMake 配置与代码调用示例。同时可查看 [《核心组件池说明》](../common_components/README.md) 了解包含哪些组件。

## 3. 各终端硬件组成与实现方式（已定基线）

### 3.1 前台管理端（Front Desk Controller）

**定位**：酒店前台的物理交互与状态展示终端，独立运行，不依赖前台电脑的 USB 数据通信。  
**部署形态概念**：**桌面控制台 / 摆件式**。采用倾斜视角的亚克力或 3D 打印外壳，置于前台桌面，便于工作人员直观查看房态灯墙与刷卡操作。

**已定硬件组成**：
1. **主控**：ESP32-S3 N16R8 (统一切换为 S3)
2. **读卡模块**：`RC522` (13.56MHz RFID)，通过 SPI 接口连接。用于读写 Mifare 实体房卡。
3. **状态展示墙**：`WS2812B` RGB 灯带/矩阵。通过单总线 GPIO 控制，每颗灯珠代表一间客房，通过不同颜色展示房态（空房、入住、清洁等）。
4. **报警与交互**：
   - 独立物理按键（警报解除、全楼广播等）。
   - 5V 有源蜂鸣器（提供刷卡成功提示音及报警音效）。
5. **本地显示（前台取消）**：前台业务侧重 PC 电脑端交互，硬件端无需配置 OLED。

**实现方式**：
- **发卡流程**：后端通过 MQTT 下发写卡指令及客房信息 `{"cmd":"write_card", "room":"301"}`，ESP32 接收后驱动 RC522 写入卡片，成功后通过 MQTT 回复后端 `{"event":"card_written", "status":"success"}`。
- **房态更新**：ESP32 订阅全量或特定房态 Topic，收到后端推送的房态变化后，解析 JSON 并改变对应 WS2812B 灯珠的颜色。
- **SOS 报警与健康自检 (Health Check)**：检测到物理按键按下触发报警；日常运行中，终端需通过 MQTT 定期（如每 10 分钟）上报系统存活状态及 WiFi 信号强度 (RSSI)，以实现故障的早期发现。

### 3.2 楼控端（Floor Controller）

**定位**：部署在酒店走廊或公共区域的纯粹数据采集与公共控制节点。  
**部署形态概念**：**弱电箱 / 吊顶暗装式**。主板与继电器隐蔽安装于走廊天花板或配电箱内，仅将温湿度探头及烟雾传感器外露于检修口，保持走廊美观。

**已定硬件组成**：
1. **主控**：ESP32-S3 N16R8 (统一切换为 S3)
2. **环境采集**：
   - `DHT11` 温湿度传感器（单总线 GPIO）。
   - `MQ-2` 可燃气体/烟雾传感器（ADC 模拟量采集，原 MQ-135 替换）。
   - `光敏电阻` 光照传感器（ADC 模拟量采集）。
3. **公共控制**：2路继电器模块（GPIO 控制，光耦隔离），用于走廊公共照明等控制。
4. **状态指示**：RGB LED（指示设备在线/异常/采集中）。

**实现方式**：
- **定时上报**：ESP32 内部设定定时器（如每 10 秒），周期性读取 DHT11 和 ADC 的数据，打包成标准 JSON 格式，通过 MQTT Publish 到后端的遥测 Topic。
- **指令执行**：订阅楼层控制 Topic，收到后端的继电器开闭指令后，拉高/拉低对应 GPIO，并通过 MQTT 回复执行结果。

### 3.3 客房端（Room Terminal）

**定位**：每间客房的独立控制中枢，负责强电控制、门禁鉴权及状态反馈。  
**部署形态概念**：**标准 86 底盒暗装 + 门外副面板**。
- **主控与强电模块**：隐藏在客房进门处的标准 86 暗装底盒内，外部面板集成 PTT 呼叫按键与 EC11 旋钮。
- **门外副面板**：通过排线延伸至房门外侧，嵌入 RC522 读卡区与门牌号指示灯。

**已定硬件组成**：
1. **主控**：ESP32-S3 N16R8 (统一切换为 S3)
2. **强电执行**：4路继电器模块（GPIO 控制，光耦隔离），分别控制客房灯光、插座、窗帘电机、电磁门锁（演示用）。
3. **微动执行**：`SG90` 舵机（模拟客房内门/窗户等微型机械动作）。
4. **门禁控制**：`RC522` RFID 模块（SPI接口，部署于房门外侧），用于住客刷卡开门。
5. **环境与存在感应**：
   - `RD-03` 毫米波雷达（串口通信），用于探测客房内人体静止存在，作为关灯/安防依据。
   - `热敏电阻 NTC`（ADC 采样），用于测量室温。
6. **红外智控**：
   - `红外发射管`：发送红外码控制客房内传统空调、电视。
   - `VS1838B 红外接收头`：用于学习并记录遥控器的红外码。
7. **反馈与报警**：状态 LED 和蜂鸣器（提供刷卡反馈音及接收到后端火警指令时的本地警报）。
8. **语音交互与广播**：
   - `LMD2718` I2S数字麦克风：用于采集语音信息。
   - `NS4168` I2S数字功放 + 3W扬声器：用于播放音频。
   - `呼叫前台` 及 `EC11` 旋转编码器：用于触发语音对讲、音量控制及菜单确认。

   **💡 AI 管家语音交互时序图 (AI Interaction Sequence)**

**实现方式**：
- **远程控制**：订阅专属客房的 Command Topic（如 `hotel/room/301/cmd`），收到开灯/开门/调温指令后，执行相应的继电器动作或发射特定红外码，随后将最新状态 Publish 给后端。
- **刷卡开门与离线应急（门禁安全级设计）**：
  - **⚠️ 纯 UID 白名单模式安全风险声明**：原需求文档中存在仅比对卡片 UID 的“离线黑名单/白名单”逻辑。由于 Mifare 卡的 UID 极易被廉价设备克隆，该方案在实际应用中存在门禁被轻易破解的严重安防漏洞，不建议采用。
  - **已定基线（扇区加密校验模式）**：本系统门禁采用高安全性**“扇区加密”**方案。前台发卡时，将加密的房客入住信息（如：房间号、过期时间戳、特征校验码）写入房卡特定扇区。客房端在线/离线刷卡时，**RC522 不再单纯读取 UID，而是通过密钥验证并读取该加密扇区数据**。客房 ESP32 解密比对房间号匹配且未过期即执行物理开门。此方案无需在断网时依赖白名单或黑名单，从根本上解决离线开锁漏洞。
- **前台广播与应急疏散（下行音频）**：ESP32 订阅专属房间音频 Topic 或全楼紧急广播 Topic（如 `hotel/emergency/evacuate`）。收到后端推送的音频流（采用极低算力开销的 **8kHz 采样率 + G.711 / PCM 编码**）时，ESP32 解析数据流并通过内部 DAC 模块输出模拟信号至 PAM8403 功放，驱动扬声器播放。此设计**坚决舍弃高保真音质（放弃复杂 Opus 解码），以“高声压、高可懂度、低算力”为目标**，确保日常通知与消防警报能够清晰、稳定地在客房内传达。
- **客房呼叫前台（上行音频 - 隐私与安全风险提示）**：
  - **⚠️ 隐私合规风险声明**：原需求文档中规划了“本地语音唤醒（Always-Listening）”功能。但考虑到客房作为高度私密空间，在主控板内部署持续监听的麦克风存在极大的隐私泄露隐患及商业声誉风险。
  - **建议修改方案（待项目组长批复）**：建议取消实时语音唤醒功能。将麦克风日常设为底层断电或挂起状态，仅在住客**主动按下“呼叫前台”物理按键**（类似对讲机的 Push-to-Talk 模式）时，才唤醒 I2S 接口读取 INMP441 数据。录音以 8kHz G.711 编码通过 MQTT 发送，并伴随明确的“📞 录音/通话中...”视觉提示，按键松开即释放麦克风资源以确保隐私安全。此方案不仅大幅降低 ESP32 算力开销，更能规避合规风险。是否采纳此修改方案，请项目组长定夺。

## 5. 全终端统一配网方案 (Network Provisioning)

**设计背景与各方案评估**：
原需求文档中提出了多种设备配网方案（包含蓝牙 BLE 配网、USB 串口配网、按键与屏幕菜单配置以及 APP 扫码配网等）。针对本系统特殊的部署环境（无屏幕终端占比高、批量部署需求大），各方案的工程属性对比与权衡如下：

1. **蓝牙 BLE / APP 广播配网**
   - **优势**：用户体验优良，支持移动端一键推送网络凭证。
   - **劣势**：在企业级复杂无线网络（如多 AP 漫游、2.4G/5G 双频合一、局域网广播包隔离）环境下，配网成功率易受干扰。同时，高度依赖前端团队针对多平台专门研发配网应用程序。
2. **本地交互界面配网（屏幕 + 按键/旋钮）**
   - **优势**：设备可独立闭环完成配置，无需借助外部计算设备。
   - **劣势**：强依赖硬件显示与输入外设。本架构中的客房端及部分楼控端属于典型的无外设节点（Headless Device），该方案无法实现全终端兼容。
3. **AP 热点模式 + Web 强制导流（Captive Portal）**
   - **优势**：设备初始化时建立独立的临时 AP 热点，移动设备连接后利用系统自带的 Captive Portal 机制强制弹出 HTML 配置页。**该方案跨平台兼容性强，无需依赖硬件屏幕及定制 APP**。借助标准开源库（如 WiFiManager）可快速实现，适用于全系统所有终端。
   - **劣势**：配置链路较蓝牙方案多一步骤（需手动将移动设备 Wi-Fi 切换至设备热点）。

**已定基线（AP + Web 强制导流配网）**：
为确保配网逻辑的代码高复用率以及现场批量施工的稳定成功率，本硬件基线**统一采用“AP 热点模式 + Web Captive Portal”方案**。
- **实施规范**：所有终端设备（前台、楼控、客房）在上电未连网或触发重置机制后，ESP32 自动开启 `AP` 模式并释放特定 SSID 热点（如 `SmartHotel_Room301`）。实施人员连入热点完成 Web 配置后，设备将凭证持久化保存至 NVS 存储区，并自动重启切换为 `STA` 模式接入局域网。此方案以极其可控的操作成本，换取了系统架构的高度统一与工程实施的鲁棒性。

## 6. 生产环境部署的安全与运维要求 (Phase 2)

为确保系统具备商用级的安全与可运维性，在完成基础功能后，全线终端设备需逐步合入以下安全管控模块：

### 6.1 通信与凭证加密 (Security)
1. **MQTT TLS 双向认证**：系统严禁在公网环境中使用明文 MQTT 协议 (`mqtt://`)。底层须启用 MbedTLS，切换至 `mqtts://` (端口 8883) 并集成后端颁发的 CA 根证书及设备客户端证书。
2. **凭证脱敏与持久化**：应用代码中严禁出现硬编码的 WiFi 密码、MQTT 鉴权令牌。上述敏感信息在首次配网时必须强制写入 ESP32 NVS（并启用 NVS Encryption 物理加密隔离），或存放于 ATECC608A 等安全芯片中。

### 6.2 异常容灾与健康审计 (Reliability & Health)
1. **消息队列等级 (QoS)**：针对开锁、消防告警等核心控制指令，MQTT 订阅与发布的 QoS 级别必须调整为 1 (At least once) 或 2 (Exactly once)，以保证网络波动时的消息不丢失。
2. **设备心跳检测 (Health Monitor)**：设备除按需上报业务事件外，还需利用 FreeRTOS 定时器周期性向 `hotel/health/xxx` 节点上报：
   - 剩余可用堆内存 (Free Heap)
   - WiFi 信号强度 (RSSI) 及重连计数
   - 固件当前版本号及运行时长
3. **断网自治 (Local Cache)**：若发生大面积断网，各终端必须仍能根据最新下发的缓存策略保证客房刷卡入室等核心功能运转，并在网络恢复后补发流水事件。
